# 当前联机版容易出错的原因：原版历史与本地实现对照

检查日期：2026-10-13（北京时间）。检查范围为已经获取的原版 main 历史（2023–2026）、本地原版 beta 基线 `1174d9f35`、本地已提交联机改动和未提交实现。没有执行完整双端对战或修改游戏代码。

## 判断

当前最主要的问题是：在一个围绕单个 Phaser 场景、阶段调度器和大量可变对象演进的单人引擎中，联机层直接插入原版阶段、手动回放事件、手动复制状态；而支持范围已经包含多种复杂战斗分支，完整集成验证还没有跟上。

原版功能规模使适配更难，但不能由源码规模或 bugfix 提交数量推断“新版整体比旧版更不稳定”。这需要相同场景下的故障统计和回归数据，目前没有这些证据。

## 已确认的直接错误：levelExp

原版 `640688239` 删除了 `public levelExp` 和构造时对它的赋值，新增：

```ts
get levelExp() {
  return this.exp - getLevelTotalExp(this.level, this.species.growthRate);
}
```

该变化早已包含在本地 2026 年 8 月的原版基线内，不是用户运行时突然更新引擎造成的。

此前我新增的 reconcileParty 使用 `(pokemon as any)[key] = data[key]`，其中包含 levelExp。PokemonData 是存档/传输数据，Pokemon 是有只读属性、方法和生命周期的运行对象，这两者不能按同名字段盲目互相复制。any 也让类型检查漏掉了此写入。

因此，这次崩溃的直接责任在我新增的同步适配代码，不能归咎于原版复杂。该项已经修复：只同步 exp 和 level，改用明确的类型化赋值，并加了复现旧异常的回归测试。

## 当前仍存在的主要风险

### 1. 联机切入范围过大，直接改变核心流程

`git diff 1174d9f35 --name-only -- src` 显示本地相对原版基线有 50 个不同的 src 跟踪文件，包括 LAN 模块和对原版战斗阶段、UI、PhaseManager 的修改。这个数量包括此前已有改动，不全是此次新增内容，也不包括未跟踪服务器文件。

联机不是只改输入来源：对局中途可能弹出替补选择、捕捉替换、学习招式、进化、奖励或遭遇选项。每一个暂停点都要求 Host、Client 和服务器对同一交互状态达成一致。当前从首发到战斗、换人、胜利和跨波次一起接入，支持范围超出了已完成的验收范围。

### 2. 阶段推进和动画结束相互关联

当前 ReplayPhase 手动改写原版动画 Phase 的 end，使其 resolve Promise，而不执行原来的阶段推进；Client 还跳过部分原版结算阶段。这是一个较脆弱的适配边界。

原版从 PhaseManager 分离到动态行动队列的历史变化说明：结束阶段、插入阶段、倒地阶段和登场特性都有明确调度规则。网络等待与回放另加一套推进流程后，某个回调漏执行、重复推进或过早 ACK 都可能导致卡住或错回合。

这属于源码确认的结构风险，不代表已经实测定位了所有卡死事件。此前已经修过回放/状态应用顺序和 ACK 等待 UI 完成；其他路径仍需完整对局测试。

### 3. 快照和校验没有覆盖完整战斗状态

本地早期提交 d956701 的终态只有场上 HP、等级、状态种类、能力阶段，甚至没有精灵 ID 和 PP。当前已经补上队伍、道具和更多字段，但服务端 ACK 比较仍只针对 `st.pokes`，不比较整个 Arena、所有后备状态、随机状态和阶段队列。

因此“ACK 一致”只说明这些已比较字段一致，不足以证明两个客户端持有完整相同的对局状态。天气/地形剩余回合、场地标签、临时效果或中途选择等，需要明确规定哪些必须同步、哪些仅在权威结算端存在。

reconcileParty 复用精灵时目前只赋一部分 PokemonData 字段，没有更新所有融合字段、nickname 等数据。源码可以确认覆盖范围有限；是否在实际对局中已触发相关显示或机制故障，此次没有实测证明。

### 4. 事件回放依赖手工覆盖

当前事件由选定 Phase 内的 log 调用采集，Client 只回放事件列表支持的类型。这不自动覆盖原版所有特性、招式和对象变化。原版加入一种机制或改变某个阶段后，Host 能正常运行，不代表 Client 的回放和对象更新已同步适配。

当前独立服务器主要管理房间和回合协议，实际战斗仍由 Host 结算。仅增加独立服务器不会自动解决引擎适配和事件覆盖问题。

### 5. 测试层级不足，是实际错误漏出的重要原因

32 项测试包括真实 WebSocket 协议测试和使用 mock 对象执行部分实际 TypeScript 代码的隔离测试，覆盖了重复行动、过期回合、席位、ACK 等问题。但没有覆盖真实 Phaser、实际 Pokemon/PokemonData、全部对象初始化、完整跨波次对局。

在 levelExp 错误出现之前，初始队伍恢复没有覆盖真实只读属性契约，因此“协议测试和类型检查通过”仍能出现入场就崩溃。这是此前验证的缺口，不应让测试数量制造已经稳定的印象。

## 对换用旧版的影响

选择 2024 年 3 月底快照可以避开后来的特殊遭遇、PhaseManager 分离和动态行动队列等复杂边界，适合重新梳理较小的支持范围。但是，该快照已经有地形、融合、Mega 和孵蛋等机制，也有自己的历史缺陷。

如果继续沿用“手工到处插入联机阶段 + 任意复制运行时对象 + 只测协议”的方法，即使换成旧版也会重现同类问题。

下一步应固定旧版契约，先验证独立单人，再做一个固定双打场景；明确一份不依赖 UI 的权威战斗状态与行动/事件协议，限制开放机制，并用真实引擎进行连续双端集成验证。完成小范围闭环后再扩大功能。

本次没有调整当前游戏代码，旧项目和未上传改动均保留。
