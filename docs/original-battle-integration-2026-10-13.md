# 原版战斗接入：依赖梳理与 B1 进度

日期：2026-10-13。对应 SPEC 阶段 B。B1 已提取第一批原版纯规则并接回单人调用；完整服务器战斗与原游戏房间界面仍未完成。

后续更新：B1 已于 `cb6afc2d` 推送；B2 首批临时效果与随机流检查点见 [状态接入记录](original-state-checkpoints-2026-10-13.md)。下文保留 B1 当时的验证范围。

## 1. 实际依赖与切分方向

| 原文件/入口 | 现状 | 接入方向 |
|---|---|---|
| `main.ts` / `BattleScene` | 启动 Phaser WebGL，持有 UI、声音、动画、战场和 Phase 队列 | 浏览器保留展示；服务器不能直接 import 整个场景当作无界面引擎 |
| `TurnInitPhase` / `CommandPhase` | 遍历场上精灵，将玩家菜单和敌方 AI 依次放入队列 | 提取“需要谁做什么决定”的数据边界；合作按席位收集输入，不按两端菜单完成时间推进 |
| `TurnStartPhase` | 特性可修改优先级；排序后插入行动、天气、回合末异常等 Phase | 保留排序、特性与插入顺序，不用简化的速度排序替代 |
| `MovePhase` / `MoveEffectPhase` / `Pokemon.apply` | 混合命中、招式属性、特性、天气、伤害、标签、消息及动画 | 逐段抽取真实规则，展示改为结果事件；完整特性/招式图仍待切分 |
| `Battle.randSeedInt` | 原先借用全局 Phaser 随机流，临时换种子再恢复 | B1 改为同算法独立实例；结果及每步序列化状态与原代码对照 |
| `Battle.getLevelForWave` / `BattleScene.getMaxExpLevel` | 波次、模式难度曲线、Boss 与成长上限公式 | B1 提取纯规则，原模式继续提供难度和最终波判定；不引入实验版等级上限 |
| `AttemptCapturePhase` | 判定在摇球动画回调中消费随机数 | B1 提取阈值及逐次判定；单人仍在原回调时机调用，保持顺序，后续服务器可无动画调用 |
| `BattleScene.getPlayerField` | 取同一个队伍数组前 1/2 只；没有玩家所有权边界 | 后续明确两个玩家各自队伍与场上槽位，不能把第二端当作独立单人场景 |
| `VictoryPhase`、奖励与商店 | 使用单份玩家资源和参与者记录 | 需要按已确认合作需求适配个人资源；经验分配等未确认点不能照抄实验均分 |
| `GameData` / `PokemonData` | 原系统档案与单人恢复，不是完整回合网络快照 | 继续保留；合作另定义完整决策状态，禁止网络字段逐个覆写 Pokemon 实例 |

采用“从原代码提取、原单人回接、原代码对照测试、最后服务器复用”的顺序。当前不采用客户端各自跑一局、直接转发主机存档、或实验引擎覆盖原版的方式。

## 2. 必须保留的原版细节

- 捕获是 **3 次随机摇球检查后锁球**，并非先前实验引擎的 4 次。不可捕获物种直接失败；大师球不消费摇球随机数；相等阈值按原版失败。球与状态倍率仍由原函数提供。
- 随机整数的范围为 `[min, min + range - 1]`；`range <= 1` 返回 min 且不消费随机数。回合种子仍是原 battleSeed 加 `turn << 6` 字符偏移，使用锁文件里的 Phaser RandomDataGenerator。
- 野生等级、Boss 与 250 波取整、每日难度曲线、经验等级上限保持原公式。没有将实验版“10 波/10 级”引入真实游戏。
- 正常 seed scope 保持原输出；唯一异常路径修正是回调抛错也用 finally 恢复外层随机流，避免后续战斗使用错误种子。
- 原图鉴字段、捕获/孵化解锁、进化前形态及 IV 联动函数没有修改。

## 3. B1 实际交付

| 文件 | 已实现内容 |
|---|---|
| `src/battle-core/random.mjs` | 不依赖 DOM/Phaser 全局的原算法随机整数与可恢复状态；同步种子作用域 |
| `src/battle-core/levels.mjs` | 原野生等级、等级偏移、经验等级上限公式，随机源由调用者提供 |
| `src/battle-core/capture.mjs` | 原捕获阈值、逐次摇球决定及随机消费语义 |
| `src/battle.ts` | 原 Battle 改为调用共享随机数与等级代码 |
| `src/battle-scene.ts` | 回接等级上限和种子作用域，异常时恢复种子 |
| `src/phases.ts` | 原捕获动画调用共享判定；球动画、声音及捕获入库流程保留 |
| `tests/fixtures/early-battle-reference.json` | 从基础提交 `2499edd7` 提取的改造前原函数片段及来源文件 SHA256，作为固定对照，不随新实现生成期望结果 |
| `tests/battle-core.test.mjs` | Node 原版兼容测试，覆盖数值、随机流状态和随机数消耗次数 |

共享模块直接使用现有 Phaser 包内的纯随机数类，不加载其渲染器、不新增依赖、不改用另一种随机算法。它可以在没有 window/document/Phaser 全局、禁用 Date.now 和 Math.random 的 Node 进程中执行。

## 4. 未解决的状态与依赖

- `Utils.randSeedInt`、部分招式和场景生成仍引用全局 `Phaser.Math.RND`。本次仅独立了 Battle 的回合随机整数，不能宣称全部随机流已经隔离。
- `executeWithSeedOffset` 仍是同步调用接口，不能包裹异步任务或让两个服务器房间共享同一个 RNG 实例。后续服务器必须为每局持有自己的随机源。
- 精灵、招式、特性和修饰器的对象关系及副作用尚未完全从 Phaser 分离；普通伤害公式也不能单独代表全部原版战斗。
- `PokemonData` 恢复时显式将 `summonData.tags` 置空（原源码 TODO），不能直接充当完整战斗恢复格式。需要覆盖临时标签、持续回合、能力阶段、招式队列、PP/PP Up、特性状态、天气/场地、Boss 段数、回合参与者与所有随机流。
- 现有回合队列含函数与 Phase 对象，不能直接 JSON 序列化。服务端检查点要落在明确决策边界，并保存后续可恢复的数据。
- 全部本局状态需要有稳定 ID 和所属席位；收藏持久化仍按原版系统存档语义，不能用战斗快照覆盖收藏。
- WebSocket 房间服务仍调用隔离的实验引擎，没有切换到这些原规则组成的完整服务器运行器。

## 5. 下一段实现与通过条件

1. 定义可序列化的战斗决策状态与事件接口，建立字段覆盖清单，明确哪些为派生值，禁止再出现写只读 getter 的恢复方式。
2. 拆分行动收集、回合排序与结算副作用，保留原特性/招式的调用顺序；用原片段与实际原游戏场景做差分。
3. 接入服务器原规则运行器后，再把房间、原初始精灵选择界面和战斗展示串起来。原选队支持的已解锁内容要完整传递，不能限制为实验目录中的 10 种。
4. 在此过程中原单人持续使用已回接的共享规则；每一段都要验证“不改变原版结果”，不能靠最终双端哈希相同替代规则兼容测试。

这只是 B1 完成条件，不等于 SPEC 的 RULE-01、GAME-01、SYNC-01 或阶段 B 整体已经通过。
