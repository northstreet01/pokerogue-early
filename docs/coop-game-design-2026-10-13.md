# 独立成长、共同战斗：需求与改造方案

日期：2026-10-13。本文记录本次用户已确认的需求与建议实现规则，不修改现有游戏代码。

## 已确认需求

- 创建房间、加入房间，可通过局域网服务器或部署的服务器游玩。
- 每位玩家从自己的本地收藏中选择 3 只精灵，同时各上场 1 只，组成共同双打。
- 个人队伍、后备、道具、奖励选择、购买和钱相互独立。
- 战斗内捕捉：谁捕获就归谁，被捕获敌人离场。
- 捕获的精灵进入捕获者的本地仓库和图鉴；个人队伍已满时，战后才可替换队伍，不插入战斗中的满队替换选择。
- 一方队伍全部倒下时，另一方继续战斗；过关后给倒下玩家恢复机会。
- 局外扭蛋、精灵收藏和图鉴在本地持久保存，不依赖官方账号或官方存档 API。
- 单人游玩也保留，使用同一套受支持的战斗规则。
- 不优先引入融合、Mega、极巨化、太晶、特殊遭遇等大量扩展机制。
- 同步的硬约束：未确认一致的战斗状态不得进入下一步决策或下一回合。

## 对局存档范围

用户回复“可以”，同意先实现断线暂停与重新接入原席位，以及战后检查点保存和继续。

任意中途退出并恢复到原选择点暂不在首版范围内；这需要保存完整的待决策状态和结算状态，不能只保存队伍 HP。

## 共享与个人状态

| 状态 | 归属与处理 |
|---|---|
| 房间、对局、波次、回合、敌方队伍、战场 | 共同，由服务器维护 |
| 行动顺序、伤害、命中、异常状态、捕捉结果、倒地与胜负 | 服务器统一结算 |
| 玩家队伍、后备和持有道具 | 各自拥有；本局状态由服务器维护，结果发给双方 |
| 奖励、商店、局内金钱 | 个人独立；服务器按个人生成并验证选择与购买 |
| 精灵仓库、图鉴、扭蛋及局外资源 | 各设备本地保存；不上传完整收藏 |
| 个人菜单、动画播放进度、音效设置 | 客户端处理，不参与战斗判定 |

“个人独立”指所有权和选择权独立。会影响共同战斗的个人数据，例如 HP、PP、等级、道具效果，仍须由权威服务器维护并同步。不能让客户端本地改好属性后直接继续对战。

## 建议架构

1. 基础参考固定到原版 `ec9365a8bffd8fa0dc050e71ef3eb177e63bc1e9`，在新目录开发。当前新版和未上传改动作为参考保留，不整套迁移当前 LAN 阶段补丁。
2. 从选定版本中梳理并抽离首版支持范围内的战斗数据与规则，形成不依赖 Phaser 场景、动画和 UI 回调的结算模块。服务器调用它；浏览器只提交行动、展示事件和权威状态。
3. 单人模式在本地调用同一规则模块，不另写一套规则。联机模式在服务器运行该模块，每次状态转移只结算一次。
4. 同一服务提供房间和战斗。局域网与部署服务器使用同一协议，通过地址配置选择服务器。
5. 局外存档单独设计，采用 IndexedDB 的事务存储和带版本的可导出文件。房间存档属于独立的对局数据，不代替个人收藏存档。

抽离战斗模块是主要工作量。需要对首版规则逐项与原版行为核对，不能假定复制旧版的整个阶段文件就能在无浏览器服务器上运行。

## 战斗同步约束

- 握手核对协议版本、规则版本与内容版本；版本不同禁止开始。
- 每个输入包含对局 ID、状态版本、决策 ID 和个人行动 ID；服务器拒绝重复、过期或不属于自己的行动。
- 双方提交行动后服务器统一结算；客户端不自行抽命中、伤害或捕捉随机数。
- 战斗随机流与个人商店、奖励和扭蛋随机流隔离，避免一方刷新商店影响战斗随机结果。
- 每次推进至明确的决策边界，服务器下发事件、完整的受支持战斗状态和状态摘要。
- 双方应用完状态并完成所需显示后确认；摘要不一致先重新下发权威状态，仍失败则暂停并记录诊断，不继续战斗。
- 倒地替补属于单独决策：仅精灵所有者选择，双方等待该决策提交完成，再继续结算。
- 超时和断线默认暂停；不替玩家选择、不跳过另一方确认。
- 网络无法保证两人的动画在同一毫秒完成；保证的是同一决策版本上的权威规则状态一致，且不允许不一致状态继续推进。
- 校验范围包括完整受支持队伍、HP/PP/状态计数/能力阶段、道具、场地持续效果、波次回合和待决策内容；随机流状态在权威端保存用于恢复和诊断。新机制加入时必须扩展状态协议和校验范围。

## 捕捉的建议规则

- 个人使用自己的精灵球，捕获成功归该玩家，敌方从共同战场离场。
- 捕获结果、球消耗、敌人离场和收藏授予由同一次权威状态转移生成，不能两端分别决定。
- 若双方同回合捕捉同一目标，按固定的捕捉行动顺序处理。建议第一个成功后，后一个捕捉行动作废且不消耗球；目标仍在场时才执行后一个捕捉。此细则为建议，尚未单独确认。
- 已捕获的实例带唯一授予 ID，立即以幂等事务加入捕获者本地仓库和图鉴。断线重发不能重复入库；断线发生在入库之前时，须能再次获取已确认授予。
- 战后由捕获者选择是否从本局新捕获的精灵中替换自己的 3 只队伍。建议首版不允许随时从全部局外仓库调入满血精灵，以免无限替换绕过本局消耗；该限制是建议。

## 奖励与购买的建议规则

- 战后进入个人整备：各自获得自己的奖励候选、金钱和商店。
- 各自选择奖励、购买物品、治疗、替换本局捕获的精灵；服务器验证归属、价格和余额。
- 一方可以先完成，但须等待另一方准备；双方准备后才生成并进入下一场共同战斗。
- 第一版不做交易、共享钱包或给另一人购买物品。
- 建议局内钱和局内道具随这次冒险保存或结束；扭蛋资源、收藏和解锁作为局外永久数据，使用不同账本。这一经济规则仍可由用户调整。
- 一方全灭后服务器只等待仍可行动的一方；全灭玩家仍看到共同战斗。战后优先提供可用恢复机会，避免无钱购买恢复导致永远无法准备。具体免费恢复或保底道具规则仍需设计。

## 本地局外存档

- 一个本地档案记录精灵实例仓库、已见/已捕获图鉴、扭蛋资源与结果、解锁和设置。
- 扭蛋消耗和获得精灵在同一事务中保存；刷新不能出现扣资源未得到精灵或重复领取。
- 对局给本地的新增收藏与奖励使用唯一授予 ID，事务去重，保留待确认授予记录。
- 保存结构版本与必要迁移逻辑，提供导出、导入和备份恢复。
- 默认按浏览器及访问来源隔离；换设备或换服务器地址后通过导出/导入搬迁档案。不是自动跨设备同步。
- 合作开始时只上传选择的队伍及必要的本局数据，服务器验证支持的精灵、招式、等级和道具规则。所有局外收藏继续留在本地。
- 第一版不要求官方账号或额外收藏服务器。

## 实现与验收顺序

1. **真实单人基础**：固定支持列表，完成结算模块、本地仓库、图鉴和存档；验证实际对象初始化、连续战斗与保存/读档。
2. **最小权威双打**：各选 3 只、各上场 1 只；房间、双方行动、主动换人、倒地替补、一方全灭、严格状态确认。
3. **完整个人整备**：双方分别选奖励和购买，捕捉归属、本地入库、满队战后替换、准备屏障。
4. **局外扭蛋与恢复**：幂等授予、导入导出、对局存档及已确认的重连范围。
5. **逐项扩展规则**：少量基础状态、招式与道具；每一类通过真实双端验收后再开放。

上述顺序用于实现，不削减用户最终需要的扭蛋、图鉴、个人商店或本地存档。

验收必须包含：不同操作速度、同时捕捉同一目标、捕捉成功导致敌方全灭、连续替补上场、一方全灭另一方胜利、购买中断线、重复输入、重复奖励、版本不匹配、刷新重连，以及连续多场双方权威状态对比。协议 mock 测试不能替代真实引擎和浏览器双端测试。
