# 《杀戮尖塔 2》同步与存档参考

2026-10-26，用户指定参考《杀戮尖塔 2》，不是第一代。以下区分开发者公开实现和本项目的取舍；不把资料中的历史设计当成当前完整源码。

## 已核实的资料

主要依据负责该作合作联机的开发者公开文章：

- [基础分层，2026-05-07](https://straypixels.net/sts2-multiplayer-architecture/)：连接经过房主转发，上层由 Lobby 和各系统 Synchronizer 管理。读档大厅向加入者发送整局序列化状态，全员准备后由房主发出开始信号。该文描述的运行中大厅不接受中途加入。
- [确定性，2026-05-20](https://straypixels.net/sts2-multiplayer-determinism/)：主要采用各端执行相同行动的确定性模型，行动后比较校验值。发现分歧时交换双方状态留作诊断并断开；文章明确当时没有任意战斗节点的自动重置恢复，只能从预定存档节点重建会话。
- [开发历程，2026-04-19](https://straypixels.net/sts2-multiplayer-timeline/)：规则与表现分离、单人与多人共享抽象、逐系统接入。附带的早期设计文档由作者明确标为历史资料，不保证等于发行实现。

这些资料没有证明其本地存储采用 SQLite，也没有给出当前完整存档格式或文件写入协议。不能据此声称本项目已经复制其底层实现。Steam 连接方式也不意味着本项目需要接入 Steam 或运营中继服务。

## 与本项目的关系

| 边界 | 本项目当前实现 | 后续采用的原则 |
| --- | --- | --- |
| 连接 | 玩家电脑托管正式服务；所有客户端连接房主 | 保留 Host-Client，玩家自己组网或映射 TCP |
| 规则计算 | 房主原 Worker 推进，客户端接收快照和事件 | 本轮保留，后续先清晰分离规则与表现 |
| 显示 | 本地 Phaser、图片、音乐、动画 | 素材不经房主传送；动画不能决定随机数和权威结果 |
| 合作局存档 | 房主本机房间目录、检查点及已接受输入 | 由原房主重开；安全节点恢复，不承诺房主自动迁移 |
| 个人存档 | 各自档案、单人进度、席位及 outbox | 各自本机持久化，不向房主发送完整个人档案 |
| 读档 | 原协议身份、席位恢复与同步屏障 | 只有正确版本、正确房间与席位才能继续，加载完成后再放行 |
| 诊断 | 原房间故障码、检查点与相关测试 | 后续记录可对比的行动序列和状态摘要，私有 token 不放进分享日志 |

“房主运行服务”已经可以实现玩家托管，开发者服务器无需承担对局计算。改变为双端规则计算并非达成 LAN 的前提。

## 后续同步演进

先集中传输、消息、会话和各系统同步职责，逐步把 Phaser 表现、资源加载、音乐、语言、计时与输入从规则边界移出。保留原版规则差分验证，再建立稳定的规则/内容指纹、随机数状态和行动记录。界面请求、模型已应用、动画播放完成应有清楚的状态关系，不能简单提前 ACK。

如果以后验证双端确定性计算确实能减轻房主负担，再独立实施“相同行动序列＋规则版本＋随机数状态＋校验”的模型。必须先验证不同语言、帧率、设备和断线时机；模型分歧时停止推进并保留诊断信息，不能悄悄用某个客户端结果覆盖其他人。本批不切换网络模型，也不取消现有安全决策点恢复能力。

## 本地存档取舍

第二批用 SQLite 原子事务保存个人资料，同时保留原 codec、档案 revision、单写者租约、历史快照和 JSON 导入导出。迁移只读取旧桌面 IndexedDB，经确认一次发布，旧资料保留。运行中的整库备份由数据库生成一致副本；恢复前先保存、留下保护副本，再重启程序。

房主合作局仍单独保存。个人库备份不等于房间备份；本人余额、成果凭据和房主检查点不能逐字段取较大值合并。永久成果与蛋进度仍按原第五批协议接入，临时退出不触发孵化。此处是本项目设计，不是对《杀戮尖塔 2》个人成长机制的描述。
