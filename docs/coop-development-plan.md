## 接下来按批次执行

用户最新要求完成整个模块后汇报。本轮目标是完整 M2，不能将下述局部测试当作完成。先补原 Phase 待续序列/进化等停点；共同地图决策和整备并行方式待用户答复，再补相应状态及恢复。见 [当前记录](decision-random-checkpoints-m2-2026-10-13.md)。下文是历史排期。

最新批次：M2 Modifier 全类型与别名恢复修复，101 项测试通过，见 [第四批记录](modifier-checkpoints-m2-2026-10-13.md)。全类型状态登记已补；Phase、全部随机调用和其他安全停点仍未补齐。按最新用户要求，下一步先开发 M3 原行动排序切片，同时继续登记 M2 依赖，不将整个 M2 提前勾选完成。

1. **M1 契约批已完成。** 先读 M1 记录及未提交变化；正式运行器默认不可用，测试模型不能作为原版规则。下一批进入 M2。
2. **M2 与原版差分/双端恢复测试一起推进。** 先登记字段与停点，再补精灵/个人资源、引用/效果、全部随机流、决策上下文。每个切片都接 M1 双端入口，不能只做单端序列化。
3. **M3 接真实原版执行。** 按决策边界分离规则，逐项通过原版行为对照；运行器不完整时列出缺口，不下调玩法范围。
4. **M4、M5、M6 按可用切片接原游戏。** 最小闭环是原 UI 选队 → 共同战斗 → 个人整备 → 下一战；正式捕获入库同时接原收藏语义，未完成前不能写错误的正式记录。
5. **M7 从第一批持续验证，M8 完成最终验收。** 不等做完 UI 才测试断线、重启和落盘失败。

故障矩阵至少覆盖：A 先提交/B 先提交、重发、同 ID 异内容、旧决策/版本、旧连接晚 ACK、损坏一端已应用状态、只收到一个行动就重启、提交成功但广播前中断、授予落盘后 ACK 丢失、服务端/客户端存储失败、两房间交错运行。验收应记录起始 revision/decisionId、故障点、恢复后结果/摘要和是否重复消耗，不记录真实凭据或个人档案。

## 进度维护规则

每次交付更新本表与 SPEC 第 5/7 节，记录模块编号、改动文件、实际测试、已知缺口、提交号和推送状态。类型、运行时实现、自动测试、浏览器验证、双机验收分别登记；只完成其中一项不能将整个模块标成已验收。

未确认玩法见 SPEC 第 8 节。可继续开发通用契约和状态基础，但相关规则落地前需确认，不能凭实验实现自行决定。
