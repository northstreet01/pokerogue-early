## 1. 产品规则

1. 无在线账号，无需我们运营账号／存档／战斗服务器。玩家本地档案是长期进度的载体；昵称、头像只用于显示。
2. 单人与正式联机使用同一份本人收藏／解锁／长期资源；两种冒险分别保存，不互相覆盖。
3. 收藏继续采用 early 按物种累计解锁的模型，不建立永久精灵实例仓库。队伍等级、HP/PP、状态、球、钱、局内道具、随机流属于冒险。
4. 单人可以离线运行；联机由房主设备上的原权威服务判定。双方各自本地启动游戏、读取本人档案，再连接房主。
5. 房主退出即合作暂停，重启原合作存档后双方恢复。第一版不做自动转移房主、公开匹配、云同步、交易或竞技榜。
6. 新大厅默认提供一份主要单人冒险；迁移时原有三个槽位均保留且可查看／继续，不能为实现“一槽”删掉旧进度。多份合作冒险可以保存，但不意味着可同时消费同一份个人蛋库存。
7. 捕获／解锁等按原版合法保存边界持续入账，不要求通关后一次发放；失败不撤销已确认的长期成果。退出不伪造未确认成果已保存。
8. 本批只设计。档案管理／保存基础、局外大厅、联机主机连接、正式长期成果、蛋／扭蛋／打包分别验收。
9. 用户追加规则：**联机过关推进蛋进度，达到条件只记为待孵化；该次合作冒险正式结束并返回局外后才孵化。** 暂按通关或双方全灭的终局理解，临时退出／断线／暂停不算终局。单人仍沿原版。此条覆盖此前任何“合作局内立即孵化”的设计。

## 2. 身份与四类状态

| 对象 | 标识／拥有者 | 职责 |
|---|---|---|
| 本地个人档案 | 新 `profileId`，由本地创建并随档案迁移 | 长期收藏、原trainer身份、个人资源与事务账本 |
| 单人冒险 | `soloRunId` + `profileId` | 原session payload及必要防重元数据，不保存另一份可覆盖收藏 |
| 合作冒险 | 持久 `runId`，房主保管 | 原完整房间文件、两席绑定和待处理成果，roomId只是房间码 |
| 本机重连记录 | `profileId + hostId + runId + seat` | 私有token、连接端点历史、outbox、主动暂停状态；不是整份合作存档 |

保留原trainerId/secretId（各16位）用于原精灵身份与规则；不能用这两个值或昵称当全局档案唯一键。`profileId`也不证明线上所有权。`hostId`用于稳定定位本地主机存档，不依赖易变IP；初次连接仍需明确地址，发现／认证细节在联机批落地。原房间版本、profile v2、decision v6/v7与新档案schema是不同版本域，不能一起随意升级。

## 3. 拟定逻辑结构

以下为字段级契约草案，不是已发布JSON codec。第二批须实现严格校验和测试，再冻结实际格式。

| 记录 | 必需内容 | 约束 |
|---|---|---|
| 档案目录 `ProfileIndex v1` | format/schemaVersion、目录revision、activeProfileId、profiles摘要 | 昵称／头像／最近使用时间仅摘要，不能作为收藏真值；切换必须关闭写者 |
| 档案包 `LocalProfile v1` | profileId、revision、createdAt/updatedAt、displayName/avatarId、originalSystem、grantLedger、deferredHatches、migration记录 | originalSystem保留原SystemSaveData；收藏与消费账本同一提交；待孵化绑定源run、本人蛋和终局释放状态 |
| 单人包 `SoloRun v1` | soloRunId、profileId、revision、status、原slot来源、originalSession、个人成果游标 | 原SessionSaveData沿用；旧session缺trainer归属，迁移绑定须说明来源和不确定性 |
| 合作目录摘要 | hostId/runId/roomId、status、玩家显示名、波次、规则版本、保存时间 | 从原房间产生，不作为权威检查点；坏一条不覆盖其他存档 |
| 合作席位绑定 | profileId、hostId/runId/seat、token、endpoint、paused、outbox | token不出现在公共摘要／日志；端点改变不改变runId，不自动跨房重放行动 |
| 个人成果账本 | grantId、sourceRunId、ownerProfileId、类型、payload摘要、提交revision | 同id同内容只执行一次，同id异内容明确冲突；不可仅按roomId／波次去重 |

`originalSystem`至少保留原训练家身份、gender、全部dexData、配招／蛋招、gameStats、unlocks、achvUnlocks、voucherUnlocks/counts、eggs及原版本。大整数属性按可恢复表示序列化，不转浮点。原新增字段须有明确兼容策略，不能因为当前界面不用就丢弃。

新档案里昵称／头像独立于原性别设定。头像只接受受支持资源ID，不允许存任意执行内容。新建与导入是两个独立入口；读取错误不能落入“首次启动”自动建空档。

设置采用全局设备偏好（音量、窗口、按键、语言）与个人教程／偏好分层；迁移完整保留原settings/tutorials和独立语言键，不强行在本批重排键。

## 4. 保存介质与单写者

逻辑模型不依赖在线服务。浏览器阶段通过现有IDB适配；正式本地发行使用固定应用数据目录，不能依赖安装目录、当前工作目录或临时域名。桌面壳／启动器技术选型另批决定，不在本批引入框架依赖。

拟定应用数据布局：

```text
用户应用数据目录/
  profile-index
  profiles/<profileId>/             个人包、单人包、个人备份
  hosts/<hostId>/formal-rooms/       原FormalRoomStore文件
  recovery/                         本机私有重连／outbox
  migrations/<migrationId>/          迁移清单、校验和、原始副本
```

每个profile同时只允许一个可写游戏流程。可以只读看收藏；不能一边单人推进一边在另一个窗口联机、扭蛋或恢复备份。用跨窗口／进程写者锁配合revision CAS，锁过期或失联时停止旧写者，不能仅靠一个布尔变量。旧实验租约不等同新全流程锁。

每次保存必须区分“内存已更新”“持久化已完成”。IDB以事务完成为准；文件以临时写、同步、原子替换为基础，并保留最后有效版本。需要目录同步／启动恢复／掉电故障验证，不能把已有rename当绝对耐久保证。建议保留最近5份有效自动快照，导入／迁移前另留固定恢复点，不被普通轮换立即淘汰。

收藏和它的去重账本必须同一原子边界。单人session与长期成果需事务化或有可重放的提交日志，不能复现当前系统先保存、session未保存导致恢复后重复领奖的问题。文件布局不意味着跨多个文件可以天然原子提交，第二批须选定包级提交或日志协议并故障测试。

## 5. 联机成果与个人蛋的后续接入契约

```text
原规则生成事实
  → 房主保存结果及有归属的待授予记录
  → 本人核对档案／run／席位／版本
  → 个人收藏与grant账本原子提交
  → 成功后grantAck
  → 房主保存确认；重发只对账
```

不要求两台设备一起完成分布式事务；采用房主待发记录与本地幂等事务。客户端已提交但ACK丢失时重发确认，房主提交失败不广播成果，本地写盘失败不发成功确认。可以离开／退出，但相关未完成决策保持待恢复，不能跳过继续。

grantId建议由持久runId、已提交事实的稳定序号／ID、接收档案和效果类型组成；同revision多个事实须可区分。旧pending先核对完整性与原始证据再转换，不凭旧实验账本补发，不把 `achievement-check` 无条件转为解锁。捕获只给本人；遇见、IV、进化链和统计沿原规则处理；券保持每席原版一份及原重复领取语义。第一批不核销任何pending。

蛋是个人库存，房间只持有该次冒险的授权镜像。需要保存库存基准revision／保留记录，避免旧合作镜像覆盖玩家后来获得的蛋，或同一蛋在单人和多个合作存档中重复孵化。

合作蛋使用以下延迟流程，后续成果／蛋批实现，不在本批改运行器：

```text
本人原蛋 → 每次共同合法过关记一次进度
        → 达到孵化条件：待孵化／锁定，不生成精灵、不消费蛋
        → 该run已持久化终局且本人返回局外
        → 原孵化生成与展示 → 收藏／蛋招／移除蛋／账本可靠提交
```

原EggLapse减进度的规则继续复用，但联机达到条件时不立即排入局内EggHatch；需适配为持久待孵化条目，不让现有hatch-commit成为整局停点。达到条件后不重复排队、扣成无限负数或每波再生成一次；内部进度是否归零需与原codec允许范围兼容，界面可显示“已就绪，冒险结束后孵化”。未达条件的剩余进度在终局后保留，不要求这一局内必须孵完。

每波进度按runId／已提交过关事实／本人蛋去重。准备满进度的蛋一直保留归属与来源run，临时回首页、刷新、重连不释放；不能转到单人立即孵化来绕过终局规则。通关或失败终局只释放已有合格蛋，不凭失败额外推进一波。显式放弃冒险若后续增加，需要走真实终止事务，不能把断线假装放弃。

终局结果已可靠保存、本人已收到对应完成记录后，可在本机局外按原蛋规则处理；不必让双方等待对方播完孵化动画。只有“保存暂停”或缺失终局确认时保持待恢复。生成结果先持久化，恢复时复用同一结果，不重抽；移除蛋与收藏／蛋招／去重记录同事务，只有生成但未提交也能继续展示／入账一次。

保守的首版策略：同一profile只激活一份会推进个人库存的冒险。离开该冒险后，先可靠对账并处理库存保留状态，才允许切换另一份；未终局的待孵化蛋继续绑定源run，不能被另一冒险消费。旧合作恢复需验证库存基准，不能整包覆盖新收藏。房主不可达、未知旧库存、旧hatch-commit未处理或库存分叉时，显示待恢复／冲突，不补空、不偷偷消费。多份冒险可保存，不承诺未实现的任意即时切换；具体可用库存过滤／释放协议在成果批验证。

旧存档已生成的hatch-commit结果必须保留，不能为了延迟规则销毁或重抽；兼容方案记录来源，按终局释放条件展示／提交或明确暂不支持该旧局。第二批只保留其数据与状态，不能提前实现孵化。

长期可研究蛋按实例保留或不同冒险并行，但不在第一版同时实现。无中央账户时，复制存档到两台离线设备产生的分支无法全局防重；第一版只支持整包选择版本／显式恢复，不做自动合并余额、次数或蛋。

## 6. 迁移流程

迁移不得直接更改旧记录。采用“扫描→只读预检→预览→目标暂存→验证→发布→保留回退”的流程。

1. 检查原写者已退出，取同一IDB快照；发现缺失、损坏、未知schema分别显示。无需读取或上传真实资料到外部服务。
2. 建立migrationId和源格式／内容摘要，原始副本完整保留。首次不联网创建profileId，原trainer身份不变。相同源重试不能再次累计资源。
3. 校验原SystemSaveData，包含枚举／目录／数值范围、大整数、蛋和解锁；不能只验证“能JSON.parse”。未知版本拒绝写入，保留原文件。
4. 三个单人槽位各自保留，不选“最高波次”覆盖其他槽；缺少原归属字段的历史槽位要求用户核对绑定，不把昵称或时间当证明。新默认继续哪个由明确选择决定。
5. 实验收藏／账本、旧凭据单独隔离保留；同trainer也不合并。正式房间pending保留在原房主文件，个人迁移不自动发奖。
6. 正式 `coop-play-v1` 需要独立迁移。先绑定profile与原host/run/seat并对照私有token，旧active/paused保持原语义；outbox保持原actionId和内容，只有同一run／席位验证成功才重发。不能仅改origin前缀重新发送。
7. 目标包写入暂存区，重读校验全部字段／摘要，验证备份和恢复点，再一次发布目录指针。中途失败仍使用旧有效数据；不留“新目录指向半份档案”。
8. 保留迁移完成标记和原始副本；回到旧版本时不自动双向同步，新旧资料同时变化则显式冲突。不同origin的数据需用户从原地址导出，不能自动跨站读取。

| 输入格式／状态 | 处置 |
|---|---|
| 当前IDB正式data／槽位 | 可迁移，需严格预检和归属确认 |
| 原 `.prsv` 系统／单人档 | 复用原解包／短键／解析，再做新结构校验；明确导入类型，不自动覆盖其他槽 |
| `pokerogue-early-backup` v1 | 兼容显式导入并展示范围；缺少正式房间／outbox不能声称联机完整恢复 |
| 旧localStorage base64数据 | 显式旧格式识别与预览；不把正常启动的缺档当成应自动转换 |
| 只有单人档、没有系统资料 | 保留为孤立冒险，待用户选择对应档案；不伪造完整收藏 |
| 未知蛋库存／旧decision v6 | 保留“未知”状态，不按空库存迁移；继续沿旧兼容或明确停止 |
| 正式房间旧版本／第24批格式 | 交由原房间codec处理，不能借局外迁移删Boss／阶段／队伍 |
| 损坏、更新版本或同ID异内容 | 原样保留并说明原因，不能清档“修复” |

## 7. 导入导出与恢复

提供三个明确范围：个人档案备份（收藏、账本、单人进度与必要的本机绑定）、房主合作存档备份、完整本机备份。用户能看见文件包含什么；含token的恢复包必须标注私密。发给朋友加入房间的邀请信息不能携带恢复token。

导入默认作为独立候选，展示冲突后选择替换／保留另一档案。相同profileId不能以“复制为新ID”的方式重复领取原run成果。恢复旧备份是整套回退，相关消费余额、蛋、receipt与库存绑定一起恢复；不能取旧余额加新账本或只回退一条记录。

摘要／校验和用于发现损坏，不证明来源真实；个人存档允许用户自行保管，无服务器认证。个人包不包含伙伴完整收藏，房主备份包含合作所需的私有队伍／凭据，不能作为公共日志发布。
