# 本地档案与冒险数据约束

更新：2026-10-27。本文描述当前实现和后续成果事务的约束，原格式以codec和接口为准，不把设计当已完成。

## 数据归属

无在线账号。本人收藏、原训练家身份、解锁、券、蛋、统计等长期资料属于本地profile。单人和联机共用本人收藏，冒险分别保存。收藏仍是early按物种累计解锁模型，不建立永久精灵实例仓库。

两种模式的GameData都通过同一个profileId读取profile.originalSystem；合作房间没有另一份永久图鉴。房间共享catalog只扩展当局选择权限。原遇见/捕获方法先更新原数据，单人随保存节点写入、联机随可靠成果事务写入，不以通关为更新前提。大厅图鉴重新读取该档案的System，图鉴浏览和三槽一览均只读，不取得写者或改变统计。

队伍实例、等级、HP/PP、状态、球、局内道具、金钱、波次、敌人、种子及随机流属于冒险。恢复安全决策还须保留已接受输入、回执、继续队列及协议元数据；不能仅保存界面正在展示的字段。

| 数据 | 拥有者与持久化 |
| --- | --- |
| 个人profile、迁移、历史 | 本机repository；桌面SQLite meta scope |
| 原单人System与Session | 固定profile IO；未选择档案时保留原单收藏兼容 |
| 个人席位与outbox | 本机seats/outbox；绑定hostId/runId/seat/profileId |
| 设备设置 | preferences有限白名单 |
| 合作检查点、输入、回执、待授予 | 原房主FormalRoomStore |
| 旧格式原始副本 | 显式迁移来源，隔离保留，不自动合并实验奖励 |

SQLite由主进程独占；渲染器只能提交有限读取/改动集合和数据库revision。repository仍独立校验profile revision、写者租约与schema；全库revision不能替代这些约束。事务函数必须同步，不得在事务中等待网络。

## 原格式与迁移

严格验证原SystemSaveData、SessionSaveData、目录枚举、数值、蛋及大整数；不能只JSON.parse。昵称/头像不等同训练家身份或席位证明。读取损坏不能当成首次启动自动建空档，未知格式拒绝写入。

迁移先只读捕获、校验、预览和确认；确认时复核同一来源摘要，再原子写入目标。相同来源重试不累计资源，保留旧IDB与原始记录。原三个单人槽位全部保留，未知归属须用户确认，不能选最高波覆盖其他槽。

旧实验收藏/账本及凭据仅作隔离来源，不给正式收藏补奖。正式席位恢复核对host/run/seat/profile及私有token；地址变动不等于可更换命名空间重发outbox。备份包含私有凭据，不提交Git。

## 保存与关闭

每个profile同时只允许一个写者，浏览收藏可只读。切档、旧回调、租约丢失和退出须停止旧写者；失效场景不能给新档案确认成果。保存完成以事务完成为准。关闭排空队列，失败留在原场景；只有明确放弃操作才允许不确认保存离开。

单人系统和冒险沿固定IO原子保存。恢复整个SQLite前留保护副本，恢复后推进revision并清理旧租约。合作房间不随个人数据库回滚；本机恢复不能伪造对端已对账。

## 联机永久成果

原规则产生事实 → 房主先保存带归属的待授予 → 本人校验绑定和版本 → 收藏变更与去重账本同事务 → grantAck。相同id异内容拒绝；ACK丢失仅重发对账，不重发奖励。捕获只给本人；遇见、IV、进化、计数、成就和券沿原方法联动，不能以简化OR/max替代。Boss券每席各一份原版份额，不能从实验账本或无凭据旧局补发。

2026-10-28 已接通新房间的永久成果：provisioning.permanentResults固定开启策略，成果payload.version=1；只授予本次已接受转换新增、带factVersion的原规则事实。旧房继续原策略，旧pending不批量补发。双方应使用新版；旧客户端遇到非空成果会拒绝确认，不允许悄悄跳过。

捕获只给捕获席位，公共遇见给双方；完整精灵事实经原setPokemonSeen、setPokemonCaught及updateSpeciesDexIvs处理，保留前置物种递归和进化不加捕获次数的语义。捕获转换前后沿同源事实去重。原成就条件在房主现场使用真实参数验证，只有achievement-approved可发放，achievement-check只作历史观察。成就授予复用原unlockAchv，Boss券分别处理原首次解锁及重复Boss普通券；胜利首次金券与重复高级券成对处理，避免双发。原Phase产生的战斗/击败/成长统计按共同或本人归属提交；不伪造在线时长。

本人先持久绑定已核对的hostId/runId/roomId/seat/profileId与私有token，再在现有写者租约和revision CAS下将原System及grantLedger一起写入。每次边界按席位批处理，账本completion表示这一组永久成果回执，具体种类保存在房主grants内；不改变个人schema。摘要检测相同ID内容或凭据变化，不能代替连接认证。事务在隔离原GameData副本上预计算，成功后刷新本人收藏；不把临时共享选队视图写入收藏。旧排队System保存通过generation检查拒绝覆盖新成果。确认只在事务成功且场景仍有效时发送。写入失败保留房主成果，界面提供“重试保存成果”，避免自动重同步循环。

双方开局的配招仅在本人图鉴的形态/技能权限也合法时保存为个人偏好；借用的物种、形态和蛋招权限不写入。新建/加入正式房间前须在大厅创建或选择个人档案；无档案的旧入口保留读取/显式迁移，不给其静默建档或补奖。

## 后续蛋事务（未完成）

合作每次合法共同过关推进原EggLapse，但满进度仅持久排队和保留库存；局内不生成、不消费、不播孵化。真实通关或双方全灭，终局已可靠保存并收到本人成果后，回局外处理。临时回首页、断线、暂停不算终局，不能切单人绕过保留蛋。单人原规则保持。

同profile保留蛋绑定源run；另一冒险不能消费或整包覆盖新库存。未知旧库存、分叉或旧hatch-commit须保留已生成结果，不补空、不重抽；无法安全转换时明确待恢复。生成结果、移除蛋、收藏/蛋招与账本须可靠提交，断线恢复展示同一结果。后续计划见[开发计划](coop-development-plan.md)。
