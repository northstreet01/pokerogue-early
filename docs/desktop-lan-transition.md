## 源码结论

现有正式service → adapter → 每房间Node Worker → 原安全检查点适合本机托管，保留唯一规则裁决。第四批已实现同一个Phaser.Game内更换Scene、缓存保留与各自本地入口连接指定房主；不重新实现大厅、规则和重连。

需要改变的是运行平台和职责：server/start.mjs把静态资源和协议服务绑在一起且依赖CWD及环境变量；start-local仍要求用户安装Node并手工构建。个人档案和outbox主要在origin隔离的IDB；桌面程序必须稳定来源及应用数据位置，旧浏览器不会自动读取。Worker固定找build/coop-runtime，发行需要与前端一起封装，不能引用用户开发目录。

native-entry仍适配原BattleScene/Phase及显示端口，最近textures.exists故障说明边界仍需收敛。打包不会自动解决规则适配、加载解码或动画卡住。play-phase快照应用仍等待enterBattle/事件回放后ACK；后续应明确模型确认、显示就绪和可输入三种状态，先保留现有安全屏障，不直接提前ACK放开下一决策。版本字符串目前固定，后续需真实规则指纹与资源清单，区分存档schema、协议、规则和纯显示资源版本，不能每次换图就拒绝存档。

## 目标结构

每个程序：本地Phaser客户端、资源包、个人档案、设置、本人席位/outbox。房主额外运行正式房间服务与原Worker，客户端照样通过同一协议连接本机。远端只传意图、结果、快照和事件，不传游戏素材或本人整包收藏。房主退出则暂停，原主机重新启动后恢复；首版不做自动房主迁移。

桌面使用Electron作为首个落地平台，保留TypeScript/Phaser/Node复用；本机资源入口只监听loopback，LAN端口只提供正式身份发现及WS，不开放档案、桌面IPC、静态资源或任意文件。renderer关闭Node集成、启用隔离和sandbox，preload仅开放具体房主命令，main核对调用来源，不通过关闭webSecurity解决跨域。

Android后续复用客户端与资源，单独验证触屏、返回键、前后台和保存。Windows房主＋Android加入是优先闭环；手机开房需要另选规则运行环境及监听/后台生命周期，不能把WebView包装当成Node Worker已经移植。不因此改写为双端独立结算。

## 实施分段

1. 首个实施批：Windows程序、完整本地素材、稳定用户数据、显式启动/停止LAN房主、原协议加入与磁盘恢复、独立构建和EXE目录。开发与8034产物隔离。当前尚未交付。
2. 平台存储接口：个人repository保持原codec/CAS/备份和单写者；先由程序固定origin的IDB保存到userData，随后提供文件/数据库后端及完整备份。现有store.transact接收JS闭包，不能跨IPC直接传函数；应把repository/事务所有者放到本地服务侧，renderer调用有限的业务命令，或使用带revision的明确事务协议。不可拆成逐键写文件伪装原子事务。席位/outbox同样迁移，host/profile/run/seat不随端口改变。
3. 原第五批：永久成果、原收藏联动、蛋进度与待终局保留，仍沿原grant事务计划。程序打包不表示这批完成；不丢pending，不提前孵化。第六批再接终局孵化/扭蛋。
4. 运行器边界：逐步归并显示、资源、消息、计时与输入端口，沿原规则差分迁移，避免继续散落patch；不要求先重写纯引擎再发桌面版。单人与联机规则共享作为长期方向，不在本批改变单人保存频率和推进模型。
5. 性能与发行：资源清单/校验、下一遭遇按需预取、解码与GPU上传测量、合理缓存释放；不是一次把全部精灵加载入显存。真实构建标识、旧档兼容、停机更新、断电与两设备LAN/玩家穿透复测；Android随后。
